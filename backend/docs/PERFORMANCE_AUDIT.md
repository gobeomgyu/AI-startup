# 성능 감사 보고서

- 감사일: 2026-10-13
- 대상: FastAPI API와 SQLite 연결 풀, 동시 쓰기 동작
- 실행 형태: 로컬 단일 서버 프로세스, SQLite 파일 DB, 루프백 HTTP

## 요약

100건 동시 작업 생성에서 초기 설정은 SQLite 쓰기 경합과 연결 대기 시간 초과로 일부 요청이 500을 반환했다. 쓰기 요청이 연결을 얻기 전에 비동기 프로세스 내 잠금에서 직렬화되도록 변경한 뒤 동일한 100건 동시 요청 재실행에서는 100건 모두 201을 받았고, 500 및 클라이언트 오류는 없었다.

이 결과는 이 로컬 단일 프로세스 구성의 동시 쓰기 동작을 검증한다. 다중 Uvicorn worker/프로세스, 장시간 부하, 원격 저장장치 또는 운영 환경 처리량을 보증하지 않는다.

## 구성과 측정 방법

- 엔진 설정(`app/db/session.py`): SQLite 풀 기본 5개, 초과 35개, 총 최대 40개 연결, 풀 대기 최대 60초, SQLite busy timeout 30초.
- 쓰기 경로는 `_SQLITE_WRITE_LOCK` (`asyncio.Lock`) 아래에서 요청 세션을 사용한다. SQLite의 단일 쓰기 특성에 맞춰 한 프로세스 안의 API 쓰기를 직렬화한다.
- 루프백 서버에 100개의 `POST /tasks` 요청을 동시에 시작하도록 barrier를 두고 응답 상태, 생성된 행, 경과 시간을 기록했다. 테스트 데이터는 기존 작업 ID 1과 구분되는 임시 작업으로 생성 후 정리했다.
- 별도로 DB 연결 세션을 병렬로 열고 쓰는 테스트를 실행해 세션/연결 자원 사용을 확인했다.

## 스트레스 테스트 결과

### 100건 동시 생성 — 초기 기준선

| 항목 | 결과 |
|---|---:|
| 동시 요청 | 100 |
| HTTP 201 | 75 |
| HTTP 500 | 25 |
| 클라이언트 오류 | 0 |
| 주 오류 | SQLAlchemy `QueuePool` 연결 대여 timeout |

서버 로그에서 풀 한도 초과와 연결 대기 timeout을 확인했다. 당시 풀은 기본 5개와 초과 10개(최대 15개), 대기 timeout 30초인 설정이었다. SQLite 단일 쓰기 잠금과 다수 동시 요청이 겹쳐 일부 요청이 연결/쓰기 구간을 제시간에 통과하지 못했다.

### 직렬화 실험 — 차단 방식 실패

초기에 동기식 `threading.BoundedSemaphore`로 쓰기를 막는 실험은 동기식 엔드포인트 작업 스레드를 대기 상태로 점유했다. 100건 요청을 완료하지 못했고, 후속 조회도 시간 초과했다. 이 방식은 최종 구현에서 사용하지 않는다.

### 수정 후 재실행 — 비동기 쓰기 잠금

| 항목 | 결과 |
|---|---:|
| 동시 요청 | 100 |
| HTTP 201 | 100 |
| HTTP 500 | 0 |
| 클라이언트 오류 | 0 |
| 생성 확인 | 100행 |
| 생성 구간 | 약 2.0초 |
| 정리 오류 | 0 |
| 요청·정리 총 시간 | 약 4.1초 |

후속 목록 조회는 HTTP 200을 반환했고 테스트 데이터는 남지 않았으며 기존 작업 ID 1은 유지됐다. 생성 구간 기준 단순 환산은 약 50 요청/초(100 ÷ 2초)지만, 단일 반복·로컬 환경의 관측치이므로 처리량 약속이나 용량 기준으로 사용하면 안 된다.

## 해석 및 제한

- 비동기 잠금은 동일 프로세스 내 여러 API 쓰기 요청이 연결을 얻기 전에 대기하게 해 스레드를 블로킹하지 않고 SQLite 쓰기를 직렬화한다.
- 최대 풀 크기 40은 동시 읽기/연결 획득 여유를 주지만, SQLite의 쓰기 병렬 처리량 자체를 높이지 않는다. 설정을 키우면 연결 및 파일 디스크립터 자원 사용도 늘 수 있다.
- 잠금은 프로세스 로컬이다. 여러 worker/process에서는 서로 조정되지 않으므로 이 결과를 다중 프로세스 쓰기 성능에 적용할 수 없다.
- 수행한 API 부하는 한 번의 100건 동시 burst다. 장시간 지속 부하, 메모리/CPU/파일 크기 추이, 읽기·쓰기 혼합 부하, 다른 디스크 및 동시 실행 서버 수를 측정하지 않았다.
- PRD/TSD에 작업·팀원 전체 목록 반환이 명시되어 있다. 따라서 대량 데이터에서의 조회·직렬화 응답 크기 증가가 잠재적 확장 한계로 남는다.

## 권고

1. 현재 단일 프로세스 로컬 배포 조건에서 이 결과를 기준선으로 삼고, DB 연결 풀 숫자를 실제 연결 점유량 관측 없이 더 늘리지 않는다.
2. `GET /tasks`와 `GET /members`의 데이터량 및 응답시간을 추적한다. 전체 반환의 운영 한계를 넘길 때 페이지네이션/필터 도입 여부를 결정한다.
3. 여러 서버 프로세스나 지속적인 동시 쓰기가 필요해지면 SQLite의 단일 작성자 제약과 프로세스 로컬 잠금으로 감당 가능한지 재검토하고, 필요 시 DB 선택과 쓰기 큐/트랜잭션 모델을 설계한다.
4. 부하 특성이 바뀌면 동시 요청 수, 요청 구성, DB 초기 데이터 크기를 고정한 반복 측정으로 비교한다.
