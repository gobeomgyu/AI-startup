# 프론트엔드 작업 루프

## 목적

에이전트가 여러 차례 작업하더라도 제품 범위와 검증 결과가 흐려지지 않도록 한다. 작은 기능 단위로 구현하고, 자동 검사와 사용자의 수동 시나리오를 근거로 완료를 판단한다. 이 문서는 작업 절차이며 제품 요구사항은 `plan.md`, 수동 테스트의 기대 결과는 `TEST_CASE.md`를 따른다.

## 작업 시작: 맥락을 좁혀 읽기

1. `AGENTS.md`와 `PROGRESS.md`를 먼저 읽는다.
2. 이번 기능에 해당하는 `plan.md` 부분과 `TEST_CASE.md`의 `M-xx` 항목을 찾는다.
3. 관련 코드와 백엔드 계약을 확인한다. 백엔드는 `C:\Users\LG\test`에 있으며 프론트엔드 구현의 기준으로 읽는다.
4. 현재 작업을 한 문장으로 적는다: **사용자 동작 → 예상 결과 → 확인할 테스트 ID**.

이 저장소에 앱 코드가 아직 없다는 사실을 숨기지 않는다. 앱이 생기기 전에는 설정과 문서만 검증할 수 있다.

## 구현: 한 번에 하나의 완결된 흐름

작업 순서는 다음 수직 기능 단위를 권장한다. 각 단위는 실제 백엔드 데이터까지 왕복해야 완료다.

| 순서 | 단위                                           | 관련 수동 테스트            |
| ---- | ---------------------------------------------- | --------------------------- |
| 1    | 앱 진입, API 연결, 목록·빈 상태·연결 오류      | M-01~M-05, M-25             |
| 2    | TODO 생성과 입력 검증, 담당자 선택             | M-06~M-11, M-27             |
| 3    | 상세 조회, 전체 필드 수정, 선택 필드·태그 제거 | M-12, M-14~M-17, M-20, M-26 |
| 4    | 빠른 상태 변경과 삭제·실패 복구                | M-13, M-18~M-19, M-28       |
| 5    | 별도 설정 화면과 두 테마의 지속성              | M-21~M-24                   |
| 6    | 모바일·키보드 최종 확인                        | M-29~M-30                   |

각 단위에서 기본 화면만 만들고 멈추지 않는다. 데이터 저장, 실패 처리, 취소, 재시도, 새로고침 후 유지까지 해당 테스트의 기대 결과를 충족한다.

## 검증: 빠른 피드백에서 전체 게이트로

1. 바뀐 순수 로직이나 API 변환에 직접 관련된 테스트를 먼저 실행한다: `npm run test -- <test-file>`.
2. 실패 원인을 수정하고 같은 테스트를 재실행한다. 무작정 동일한 명령을 반복하지 않는다.
3. 단위가 완성되면 `npm run check`를 실행한다. 이 명령은 lint → format:check → typecheck → test 순서로 실패 시 중단한다.
4. 앱과 백엔드가 실행 가능한 환경에서 관련 수동 테스트를 수행한다. 수동 결과는 자동 테스트 통과로 대체하지 않는다.
5. `PROGRESS.md`에 완료한 단위, 실행 명령과 결과, 수동 테스트 ID, 미검증 사유를 남긴다.

자동 테스트는 상태 매핑, 입력 정규화, API 오류 처리처럼 회귀 위험이 있는 동작을 검증한다. 단순 렌더링 결과를 코드와 같은 문장으로 확인하는 테스트는 만들지 않는다. Playwright E2E 테스트는 만들지 않는다.

## 실패 처리와 종료 조건

- 검사 실패: 첫 오류를 재현하고 원인을 수정한다. 설정을 느슨하게 하거나 테스트를 건너뛰어 성공으로 표시하지 않는다.
- 백엔드 또는 npm 접근 불가: 명령, 오류, 미완료 검증을 기록하고 독립적으로 진행 가능한 작업을 한다.
- 같은 실패가 두 번 반복됨: 다른 원인 가설이나 입력을 정한 뒤 재시도한다.
- 단위 완료: 해당 동작이 실제 데이터에 반영되고 관련 자동 검사 및 수행 가능한 수동 테스트가 통과해야 한다.
- 사용자 인계: 변경 파일, 통과한 검사, 미실행 검사와 이유, 다음 단위를 짧게 전달한다.

커밋 전 `pre-commit` 훅도 `npm run check`를 실행한다. 현재 저장소에는 아직 앱 코드와 자동 테스트가 없으므로 이 게이트가 통과하지 않는 상태가 정상이다. 실제 테스트가 생길 때까지 빈 테스트 통과를 허용하지 않는다.
